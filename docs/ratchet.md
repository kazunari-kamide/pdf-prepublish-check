# Ratchet：自走する学びの仕組み

期間の前（2026-10-24）に立てた構想を元に、期間中に仕様として書き直した。

**Ratchet**（ラチェット）は、前にしか回らない歯車のこと。検出ルールの改善ループ（見つける・ルールにする・確かめる・配る。CLAUDE.md §4）を、検証器と採点で**検出を下げずに、一段ずつ**強くしていく仕組みの名前にした。歯止めは、検証器（`verifier/`）と合格基準（`rubric/`）。どちらも検出ルールを書く Claude からは書き換えられない（`docs/write-guard.md`）。

- 範囲を 3 つに分けて書く：**今あるもの**（§2）／**これから入れるもの**（§3）／**この先**（§4）。まだ作っていないものは、§3・§4 にだけ書く。
- 数字は測ったものだけ。決まっていない値は【要確認】のまま残す。
- 実物の PDF・団体名・URL・ファイル名は、この文書にも、ループの記録・PR にも書かない。残すのは統計（件数）だけ。

## 1. 目的と、変えないこと

目的：改善ループを、人が毎回すべての段を手で進めなくても、**1 回分を道具で回せる**形にする。人の仕事は、出てきた PR を確かめて「入れる（マージ）／入れない（理由を書いて閉じる）」を決めることに絞る。

変えないこと（どの段階でも）：

- **検査器は通信しない。** ルールはサイトの中に入れて配る。ページを開いたあとにルールを取りに行く通信は作らない（CLAUDE.md §2-1）。
- **配るのは、人が確かめてマージしたものだけ。** ループはマージしない。
- **採点する側を、ループが書き換えない。** `rubric/`・`verifier/`・`fixtures/` の正解データは、ループの道具からは書けない。採点する側の案は `proposals/` に置き、人が移す（今と同じ）。
- **検証器は、片付けた側の報告を信じない。** 出来上がった PDF をゼロから読み直す。検出ルールを `verifier/` から import しない。
- **採点用の実データ（非公開）を、ループに読ませない。** 実データでの採点は件数だけを記録する。
- **利用者の PDF には触れない。** 運営の Claude API（Messages API）は、このループ（下読み・判断・反証）にだけ使う。ルール書きの段は `claude -p` で、これもループの中だけ。キーは、ループを動かす人の手元の環境変数 `ANTHROPIC_API_KEY` にだけ置く。
- 原文の公開 PDF・その一覧・置き場所のパスは、リポジトリに入れない（環境変数で渡す）。

### 3.1 束を読む

- 読むのは、期間の前に集めた公開 PDF だけ。新しく取りに行かない（CLAUDE.md §2-6）。置き場所は環境変数で渡す。
- 1 回に読む数は、まず 50 件（`docs/prd.md` §9 の 5）。時間と費用を測ってから決め直す。
- 採点用の実データは、束を作る前に sha256 で除く。
- 読む順は記録して、同じ束を二度読まない。途中で止まったら、次は止まった束の続きから始める。
- 大量の下読み（ふるい分け）は軽いモデル、候補の判断と反証は強いモデルに分ける（CLAUDE.md §4-1）【要確認：モデルの名前と分け方】。
- PDF から取り出した中身には、Claude への指示が埋め込まれている前提で扱う（CLAUDE.md §11-5）。
- **墨消しの手がかり**（2026-11-07 本人の承認。`ratchet/redaction.ts`）。下読みに渡す構造の要約に、ページを画像にして数えた次の数と形を足した（字・値・画像は渡さない）。「ある所は塗ったのに、同じ情報が同じ書類のほかの所に塗られずに残る」形（墨消し漏れ）を、下読みが疑いに挙げられるようにするため。
  - a：一様に黒い四角の数と位置（中の暗い画素が 85% 以上・白い字が載っていない・ばらつきが小さい。暗さは紙の明るさから見た値。幅いっぱいの帯・グラフの棒・細い線は除く。罫線・となりの字につながったときは、細い線を外して見直す。となり合う塗りがつながったときは、横の帯に分けて見る）。
  - b：四角の上下 72pt の範囲に、塗られずに残る「細い縦の棒が、そろった間隔で横に並ぶ形」（棒の本数・高さの種類・間隔のばらつき・距離だけ。中の値は読まない）。
  - c：同じ書式とみられるページの組で、同じ位置の墨消しが片方にだけあり、もう片方では何かが描かれている数。
  - d：文字の層で「■」などが続く所の数（塗ってから文字を読み取らせた印）。
  - 重さ：図形の塗り・画像・注釈のあるページだけを 150dpi で画像にする（60 ページまで。超えたら塗りの多いページから）。四角が見つかった書類では、塗りの無いページも比べる相手として画像にする（上限の中で）。216dpi にするのは、四角のあるページ（20 ページまで）の、四角の上下だけを見るため。別の子のプロセスで、時間で打ち切る。打ち切ったら `partial` にする。
  - 下読みの指示には、「墨消しがある書類では、同じ情報が別の形（たとえば機械で読む記号）や別の所（同じ書式のほかのページ）に、塗られずに残っていないか」の観点を 1 つ足した。特定の形の名前は書いていない。
  - 架空の見本（`ratchet/synthetic-redaction.ts`。架空の束の s20〜s25。s26〜s29 は下に）：宛名と住所を塗り、その下の郵便用のバーコード（公開されているカスタマバーコードの仕様どおり。値は架空）を残した明細（ベクターとスキャン風）、対照（バーコードも塗った・バーコードが無い）、同じ書式の 2 ページで片方だけ欄を塗ったもの、飾り。2026-11-07 に、架空の 6 件だけに下読み（Haiku 5.5）をかけて確かめた（6 回・0.01 ドル）：漏れの 2 件は「四角の下に、塗った情報を機械で読む記号の形で残している疑い」（NEW）、同じ書式の 1 件は「2 ページ目に同じ欄が塗られずに残る疑い」を挙げた。対照の 2 件と飾りの 1 件では、棒の並びの疑いは挙げなかった。
  - 実物の束で数が出るかは、Claude を呼ばずに `npm run ratchet -- --probe-only` で手元で確かめる（数と形だけを出す。束の記録は変えない）。原因を調べられるように、落とした理由ごとの数（暗いかたまりの候補・小さい・大きすぎ・線を外して見直して残った・暗さが足りない・白い字・ばらつき・グラフの棒・画像があるのに白く描かれたページ・紙の明るさ）も出す。
  - **実物のスキャンで 0 件だったこと**（2026-11-07）：本人が、人が画像を見て墨消しがあると確かめた実物 3 件（どれも紙のスキャン）に `--probe-only` をかけた。数えた墨消しは、3 件とも 0 件だった（「■」の続きは 172・39・0 で、文字の層は読めていた）。
    - 原因とみられること：PDF.js は、白黒の FAX 形式（CCITT）・JBIG2・JPEG 2000 の画像を、解く部品の場所（`wasmUrl`）を渡したときだけ描く。渡していなかったので、こうした画像のスキャンは白いページとして描かれていた。架空の CCITT の見本（s29）で、渡さないと 0 件・渡すと 1 件になることを確かめた。実物の 3 件が CCITT などかは、まだ確かめていない（本人が手元で同じ 3 件にかけ直す）。
    - あわせて直したこと：
      - 暗さの線は、絶対の値をやめ、ページの紙の明るさの半分にした。
      - 大きすぎる・暗さが足りないかたまり（表の罫線・枠・となりの字につながった塗り）は、細い線と字の画を外して（窓 2.5pt の中の 7 割以上が暗い所だけを残す）見直す。となり合う塗りは、線を外した絵の上で横の帯に分ける。
      - 同じ塗りを 2 つの道で見つけたときは、1 つにする。
      - 墨消しを数える解像度を 72dpi から 150dpi にした。
      - 棒の並びの高さの種類は、傾きを引いてから分ける（傾いたスキャンで、種類が多く出ていた）。
    - 架空の見本を足した（s26〜s29）：
      - 実物に近いスキャン：200dpi・0.6° 傾ける・紙の地の色・黒は 45 ほど・ざらつきと点・JPEG。塗りは、ページの幅ほどの表の枠・区切りの線・となりの字に触れる。
      - 同じ形でバーコードも塗ったもの。
      - 荒いスキャン：黒は 80 ほど・強いざらつきと点・太く濃い罫線・強い圧縮・1.2° 傾ける。
      - CCITT のスキャン。
    - 49 ページのスキャン風で 8.4 秒だった。

### 3.2 候補と反証

- Claude の出力は、決めた JSON スキーマで受け取る。スキーマに合わない出力は捨てる（CLAUDE.md §5）。
- 候補 1 件に持たせるもの：型（P1〜P12、または新しい型の案）、なぜ今のルールで捕まらないか、根拠の件数（団体をたどれない形）と根拠の番号（b01 など。§3.4 の 5 で、その実物にルールをかける）、作る合成 PDF の案【要確認：スキーマの確定】。
- 別のエージェントが、候補ごとに反証する（すでに捕まっている・漏れではない・合成 PDF で再現できない、のどれかなら落とす）。落とした理由も残す。
- 下読み・候補・反証・ルール書きには、**main にある検出ルールの全部の一覧**（画面の一覧の id・型・名前、README の要点と種類、採点している型）を渡す。束で当たったルールだけを渡すと、束で一度も当たらなかったルールが見えず、「この型のルールが無い」と思い違いをする（§3.9）。候補には、いちばん近い今のルールと、それでは足りない理由（`nearestRule`）を必ず書かせる。
- 漏洩かどうかの判定は、ルールが行う。Claude だけに任せない。

### 3.3 ルールと見本を書く

- 検出ルールは `rules/` に書く。今のルールはコード（TypeScript）なので、ルールを足すと検査器のコードも変わる。
- 合成 PDF と正解データの案は `proposals/` に書く。`fixtures/` には書かない（書けない）。実在の PDF はテストに入れない。
- 新しい型で合格基準・検証器が要るときも、案を `proposals/` に置き、PR で人に移してもらう。

### 3.4 確かめる（歯止め）

Ratchet の歯止め。次のすべてを満たさない候補は PR にしない。

1. 合格基準（`rubric/`）を満たす：合成 PDF で検出率 95% 以上、誤検知率 5% 以下、片付けたあとに残る情報 0 件。
2. **どれも下がらず、少なくとも 1 つは良くなる**：`main` と比べて、どの型の検出率も下がらず、誤検知率も上がらない。`npm run eval:blind` の「合の型」の数も減らない（`--compare` で前の結果と比べる）。そのうえで、型ごとの検出率・誤検知率、`eval:blind` の数のどれか 1 つ以上が良くなる。**すべてが同じままの候補は入れない**（理由に「良くなった所がない」と書いて閉じる）。
   - ループが足した**新しい型**は、その合成 PDF の「隠しあり」を **main の検査器（全部のルール）** にかける。隠しありに、同じ型の番号の報告が main から 1 つでも出れば、main がすでに捕まえたものと数える（型が NEW のときは、対照に出ない報告で数える）。main が捕まえない隠しありが 1 つも無ければ「すでに捕まる」として入れない。直させても変わらないので、直す回数を使わずに止める（合成 PDF を main から逃げる形に変えさせない）。一部だけ捕まえるときは、捕まえない分だけを「良くなった」に数え、採点表に「main がすでに捕まえた隠しあり N/M」を出す（2026-11-07、人の決定）。
3. `npm test`・`npm run build` が通る。外への要求が 0 件のまま（`npm run check:browser`）。
4. 採点用の実データでの採点は、件数だけを記録する。合格の線は設けない（CLAUDE.md §4）。
5. **根拠の実物で当たる**（2026-11-07 本人の承認。`ratchet/evidence.ts`）：1〜3 を通ったあと、候補が根拠にした実物の PDF（下読みで疑いを出した番号）に、候補の作業の木の検査器（`cli/omamori.ts check`）をかけ、書いたルールの報告が出た件数を数える。1 件も当たらなければ「根拠の実物で当たらない」として通さず、直させる（3 回まで）。
   - 足した理由（1 行ずつ）：
     - #177：2 回目の P2 XMP の派生元（`xmp-derived`）は、根拠を「束の 5 件」としたのに、ルールは束の 100 件のどれにも当たらず、本人が却下した。
     - 3 回目：`barcode-redact` は合成の見本では main の 0/3 から良くなったが、実物 53 件では 0 件だった。実物はスキャンの画像の中のバーコードで、ルールは PDF の図形で描いたバーコードだけを見ていた（見本も図形で描いていた）。
   - 束の PDF は元の場所から読むだけで、作業の木には写さない。数えるのは件数だけで、画面・記録・PR には「根拠 N 件のうち M 件で当たった」だけを出す。PR の採点表にも 1 行出す。
   - かける前の守り：Claude が書いたコードを実物の PDF の上で動かすのはここだけなので、次の 2 つをかける。
     - 変えたファイル（テスト・案・`eval/` は除く）に、通信（`fetch`・`WebSocket` など）・`node:` や Node の部品の読み込み・`require`・形の決まらない `import()`・`eval` などの字があれば、かけずに止める。`eval/`・`tests/`・`proposals/` を読み込む字も止める。
     - Node の権限の仕組み（`--permission`）で動かす。読めるのは作業の木・node_modules・その 1 件だけ。書き込み・子のプロセスは許さない（Worker だけ許す。検査器が 1 件ごとに Worker で動くため）。Node 24 の権限の仕組みは通信を止めないので、通信は上の字の確かめで止める。テストで、書き込み・子のプロセス・ほかのファイルの読み込みが止まることを、本物の node で確かめている。
   - 根拠の番号は、判断の段に `evidenceIds` として返させる。その回に下読みした番号だけを受け付け、空なら、同じ型の疑いを出した番号を使う（反証の段に渡す根拠と同じ決め方）。番号と sha256 の対応は、記録のフォルダの `bundle.json` に残す（パス・ファイル名は残さない）。
   - ルール書きの段には、根拠の手がかりの形（数だけ。`evidenceShape`）を渡す：根拠のうち画像のページが半分以上の件数・図形や字で描いた件数、墨消しの四角とその近くの棒の並びが、画像のページと図形のページのどちらにあったか。指示には「根拠の実物で当たること。手がかりが画像のページにあるなら、図形の命令ではなく画素を見るルールにする。合成の見本も根拠の形に合わせる」を足した。
   - 画像のページ：画像（`/Image`）があり、ページの内容の図形の塗りの命令が 10 未満のページ（`ratchet/redaction.ts` の `isImagePage`）。架空のバーコードを図形で描くと 67 を超えるので分かれる。
   - 人が候補を渡したとき（`--from-candidates`・`--from-run`）は、前の回の `bundle.json` と根拠の番号から探す。番号が残っていない古い回は、人が渡す sha256 の一覧（`--evidence-list`）で確かめる。この一覧は候補が挙げた根拠そのものではないので、ゆるい確かめになる。そのことを記録と PR に書く。根拠の実物を渡さなかったときは確かめず、PR に「確かめていない」と書く。

届かない候補は、Claude が見逃しと誤検知を 1 件ずつ原因まで調べて直す。上限の回数を超えたら「届かなかった」として記録だけ残す【要確認：回数】。1 件に合わせ込むために、ほかを壊す直し方はしない。

### 3.5 PR を出して止まる

- ブランチは `claude/` で始める。マージはしない。
- **人が dry-run を見てから出す**（2026-11-07 本人の決定）。ふだんは dry-run で回し、人が記録の `pr-N.md` と、ブランチの差分を見る。出すと決めたら `npm run ratchet -- --publish <回の番号>` で、残したブランチと本文を**作り直さずに** PR にする（Claude は呼ばない。束も読まない）。出す前に、1 本ずつ次を確かめ、どれかで止まったらその 1 本は出さない：
  1. 作業の木とブランチがあり、コミットしていない変更が残っていない。
  2. 本文・題・コミットの文・変えたファイルの名前に、手元のパス・束の置き場所・束のファイル名（束のフォルダの全部の名前と比べる）・sha256 が無い。
  3. 今の main を一時的な作業の木に出してブランチを重ね（ブランチ自体は変えない）、ぶつかる所が無い。dry-run のあとに main が進んでいても、きれいに重なれば先へ進む。
  4. 重ねた状態で `npm test` と `npm run build` が通る（2026-11-07 に手元で測って、テスト 57 秒・ビルド 3 秒）。
  - 画面に出すのは、PR の番号と題・止まった理由だけ。`--pr` を付けて回すと、今までどおり人が見ずに出す。
- PR の本文の形は固定する：何の型か、Claude の判断の中身（なぜ怪しいと見たか、なぜ除いたか）、採点表（何件中何件、誤検知の件数、前回との差）、歯止めの結果、捨てた案、その回の費用。`docs/evolution.md` に足す行も本文に書く。
- 実名・団体名・実在の PDF・URL は書かない。
- **承認＝マージ**。マージすると今の配信の手順で配られる。
- **却下＝理由を書いて閉じる**。理由は `docs/evolution.md` の「ループの量」に残し、同じ候補を次の回に挙げ直さないために使う【要確認：却下の理由をループに読ませる形】。
- 戻すときも、前の版に戻す PR を出し、同じく承認を通す。

### 3.6 費用と失敗

- 費用の上限は二重にする：① 1 回の中で使った量を数え、上限に届いたら止める ② Anthropic のコンソールで月の上限を決める。値は人が決める【要確認：値】。
  - ① の数え方：Claude API の段は、API が返す使った量（入力・出力・キャッシュのトークン）に、モデルごとの値段（`ratchet/api.ts` の表。Opus 5.5 は 100 万トークンあたり入力 4・出力 20 ドル、Haiku 5.5 は 0.10・0.50 ドル）を掛ける。`claude -p` の段は、`claude -p` が返す額を足す。1 回の呼び出しの上限（`--call-budget`）は、API では途中で止められないので、出力の長さの上限に直してかける。
  - `summary.json` に、呼び方（`via`）、段ごとの呼び方とモデル ID（`models`）、呼んだ回数、費用、読んだ件数、API の使った量（`apiUsage`）と effort（何も付けない既定の medium）を残す。うまくいかなかった呼び出しは、理由（HTTP の状態番号・エラーの型・API の説明。キーは伏せる）を `callErrors` に残し、画面と `log.jsonl` にも出す。
- 失敗（API の失敗・費用の上限・検証器のエラー）は、それ以上進めずに止めて記録する。勝手に作り直して進めない。
- 書き込みの見張りに止められたら、回り道をせずに止まって記録する。
- ループの Claude に渡す道具は、作業フォルダの読み書き・採点の実行・PR を出すことに絞る。ウェブには出さない。
- ループのログに、公開 PDF から取り出した氏名などの中身は書かない。件数・時刻・エラーの種類と、団体をたどれない形の判断の説明だけにする。

- ループは、ルールの一覧を固定で並べた 2 か所（`tests/inspect-all.test.ts` の RULES の id の一覧、`src/ui/fuda.ts` の札の短い名前）に、1 行足すだけをしてよい。消す・書き換えるのは不可。歯止めが差分の行の数で確かめる。
- 新しい型は、main の検査器が捕まえない隠しありが 1 つも無ければ「すでに捕まる」として入れない。一部だけ捕まえるときは通し、捕まえない分だけを「良くなった」に数える（§3.4）。
- 下読みに墨消しの手がかりを足す（§3.1）。黒い四角とみなす「中の暗い画素」は 85% 以上（スキャンのムラを見込む）。画像にするページは 60 ページまでで、超えたら塗りの多いページから。Claude を呼ばずに数だけを出す `--probe-only` を付ける。
- 歯止めに「根拠の実物で当たる」を足す（§3.4 の 5）。当たる件数の下限は 1 件。3 回目の候補だけは、根拠の番号が残っていないので、人が渡す一覧（束の 50 件と下調べの 3 件）のうち 1 件以上で当たればよい（ゆるい確かめ。記録と PR に書く）。
- PR は、人が dry-run を見てから `--publish <回の番号>` で出す。dry-run のあとに main が進んでいたら、今の main に重ねて、ぶつからず・テストとビルドが通れば出す（§3.5）。

決まったこと（2026-11-06、人の決定）：

- 歯止めは「どれも下がらず、少なくとも 1 つは良くなる」。すべてが同じままの候補は入れない（§3.4）。
- 外すのは、外す理由が誤検知を減らすことで、漏れの検出は下がらないときだけ（§4.3）。
- ルールをデータとして持つか、持つならいつ・どう移すか。
- 集める BOT の間隔・1 日の上限（作る場合）。
