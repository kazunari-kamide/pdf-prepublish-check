# Ratchet：自走する学びの仕組み

期間の前（2026-10-24）に立てた構想を元に、期間中に仕様として書き直した。

**Ratchet**（ラチェット）は、前にしか回らない歯車のこと。検出ルールの改善ループ（見つける・ルールにする・確かめる・配る。CLAUDE.md §4）を、検証器と採点で**検出を下げずに、一段ずつ**強くしていく仕組みの名前にした。歯止めは、検証器（`verifier/`）と合格基準（`rubric/`）。どちらも検出ルールを書く Claude からは書き換えられない（`docs/write-guard.md`）。

- 範囲を 3 つに分けて書く：**今あるもの**（§2）／**これから入れるもの**（§3）／**この先**（§4）。まだ作っていないものは、§3・§4 にだけ書く。
- 数字は測ったものだけ。決まっていない値は【要確認】のまま残す。
- 実物の PDF・団体名・URL・ファイル名は、この文書にも、ループの記録・PR にも書かない。残すのは統計（件数）だけ。

## 1. 目的と、変えないこと

目的：改善ループを、人が毎回すべての段を手で進めなくても、**1 回分を道具で回せる**形にする。人の仕事は、出てきた PR を確かめて「入れる（マージ）／入れない（理由を書いて閉じる）」を決めることに絞る。

変えないこと（どの段階でも）：

- **検査器は通信しない。** ルールはサイトの中に入れて配る。ページを開いたあとにルールを取りに行く通信は作らない（CLAUDE.md §2-1）。
- **配るのは、人が確かめてマージしたものだけ。** ループはマージしない。
- **採点する側を、ループが書き換えない。** `rubric/`・`verifier/`・`fixtures/` の正解データは、ループの道具からは書けない。採点する側の案は `proposals/` に置き、人が移す（今と同じ）。
- **検証器は、片付けた側の報告を信じない。** 出来上がった PDF をゼロから読み直す。検出ルールを `verifier/` から import しない。
- **採点用の実データ（非公開）を、ループに読ませない。** 実データでの採点は件数だけを記録する。
- **利用者の PDF には触れない。** 運営の Claude API はループにだけ使う。
- 原文の公開 PDF・その一覧・置き場所のパスは、リポジトリに入れない（環境変数で渡す）。

## 2. 今あるもの

今のループは**人が起こして、段ごとに手で回している**。道具としてまとまった「1 回分を回す仕組み」はまだない。

| 段 | 今のやり方 | 使っているもの |
|---|---|---|
| 見つける | 人が頼み、Claude Code のセッションが、期間の前に集めた公開 PDF の束を読んで、今のルールで捕まらない漏れ方の候補を挙げる。候補を入れるかは人が決める | Claude Code（対話のセッション） |
| ルールにする | 検出ルールを `rules/<名前>/`（TypeScript のコードと README）に書き、画面の一覧 `src/inspect/rules.ts` の `RULES` に足す。採点する側（合格基準・検証器・合成 PDF と正解データ）の案は `proposals/` に置き、人が `rubric/`・`verifier/`・`fixtures/` へ移す | `rules/`、`proposals/` |
| 確かめる | 合成 PDF と正解データで採点する。片付けたあとの残りも測る | `npm run eval`（型ごとは `eval:p6` など）、`npm run eval:sanitize`、`npm run eval:blind`（型の一覧の説明だけから作った、見ないで作るテスト集）、`npm test` |
| 配る | `claude/` で始まるブランチから PR を出す。人がマージすると、GitHub Actions がビルド・テストをして配信する | GitHub の PR、`.github/workflows/deploy.yml`（`docs/deploy.md`） |
| 記録 | 改善の 1 行（検出率・誤検知率の前→後、何を直したか、理由、捨てた案）、ループの量、Claude と人の判断の一致を残す。行は PR の本文に書き、マージのあとに足す | `docs/evolution.md` |

ほかに今あるもの：

- **書き込みの見張り**：権限の拒否（deny）とフック（`.claude/hooks/guard-writes.mjs`）で、採点する側への書き込みを止める。止められないこと（スクリプトの中の書き込みなど）も `docs/write-guard.md` に書いてある。
- **画面の「ルールの版」**：検査の結果の下に、使った検出ルールの版・更新日・最近足した型を出す（`src/ui/ruleset.ts`）。更新日と「最近足した型」は、ルールを足したときに手で直している。
- 定時に自動で回す形（予定タスク・`/loop`）は、まだ入れていない【要確認：PRD の作業計画どおりに始めたかを確かめて直す】。

## 3. これから入れるもの：1 回分のループを回す道具

人が 1 回起こすと、次の段を順に進め、**PR を出したところで止まる**道具。

```
集めた公開 PDF の次の束を読む → 候補を挙げる → 別のエージェントが反証する
  → ルールと見本（合成 PDF・正解データの案）を書く → 検証器と採点にかける
  → 歯止め（§3.4）を通ったものだけ PR にする → 止まる
人：PR を確かめて、承認＝マージ／却下＝理由を書いて閉じる
```

### 3.1 束を読む

- 読むのは、期間の前に集めた公開 PDF だけ。新しく取りに行かない（CLAUDE.md §2-6）。置き場所は環境変数で渡す。
- 1 回に読む数は、まず 50 件（`docs/prd.md` §9 の 5）。時間と費用を測ってから決め直す。
- 採点用の実データは、束を作る前に sha256 で除く。
- 読む順は記録して、同じ束を二度読まない。途中で止まったら、次は止まった束の続きから始める。
- 大量の下読み（ふるい分け）は軽いモデル、候補の判断と反証は強いモデルに分ける（CLAUDE.md §4-1）【要確認：モデルの名前と分け方】。
- PDF から取り出した中身には、Claude への指示が埋め込まれている前提で扱う（CLAUDE.md §11-5）。

### 3.2 候補と反証

- Claude の出力は、決めた JSON スキーマで受け取る。スキーマに合わない出力は捨てる（CLAUDE.md §5）。
- 候補 1 件に持たせるもの：型（P1〜P12、または新しい型の案）、なぜ今のルールで捕まらないか、根拠の件数（団体をたどれない形）、作る合成 PDF の案【要確認：スキーマの確定】。
- 別のエージェントが、候補ごとに反証する（すでに捕まっている・漏れではない・合成 PDF で再現できない、のどれかなら落とす）。落とした理由も残す。
- 漏洩かどうかの判定は、ルールが行う。Claude だけに任せない。

### 3.3 ルールと見本を書く

- 検出ルールは `rules/` に書く。今のルールはコード（TypeScript）なので、ルールを足すと検査器のコードも変わる。
- 合成 PDF と正解データの案は `proposals/` に書く。`fixtures/` には書かない（書けない）。実在の PDF はテストに入れない。
- 新しい型で合格基準・検証器が要るときも、案を `proposals/` に置き、PR で人に移してもらう。

### 3.4 確かめる（歯止め）

Ratchet の歯止め。次のすべてを満たさない候補は PR にしない。

1. 合格基準（`rubric/`）を満たす：合成 PDF で検出率 95% 以上、誤検知率 5% 以下、片付けたあとに残る情報 0 件。
2. **どれも下がらず、少なくとも 1 つは良くなる**：`main` と比べて、どの型の検出率も下がらず、誤検知率も上がらない。`npm run eval:blind` の「合の型」の数も減らない（`--compare` で前の結果と比べる）。そのうえで、型ごとの検出率・誤検知率、`eval:blind` の数のどれか 1 つ以上が良くなる。**すべてが同じままの候補は入れない**（理由に「良くなった所がない」と書いて閉じる）。
3. `npm test`・`npm run build` が通る。外への要求が 0 件のまま（`npm run check:browser`）。
4. 採点用の実データでの採点は、件数だけを記録する。合格の線は設けない（CLAUDE.md §4）。

届かない候補は、Claude が見逃しと誤検知を 1 件ずつ原因まで調べて直す。上限の回数を超えたら「届かなかった」として記録だけ残す【要確認：回数】。1 件に合わせ込むために、ほかを壊す直し方はしない。

### 3.5 PR を出して止まる

- ブランチは `claude/` で始める。マージはしない。
- PR の本文の形は固定する：何の型か、Claude の判断の中身（なぜ怪しいと見たか、なぜ除いたか）、採点表（何件中何件、誤検知の件数、前回との差）、歯止めの結果、捨てた案、その回の費用。`docs/evolution.md` に足す行も本文に書く。
- 実名・団体名・実在の PDF・URL は書かない。
- **承認＝マージ**。マージすると今の配信の手順で配られる。
- **却下＝理由を書いて閉じる**。理由は `docs/evolution.md` の「ループの量」に残し、同じ候補を次の回に挙げ直さないために使う【要確認：却下の理由をループに読ませる形】。
- 戻すときも、前の版に戻す PR を出し、同じく承認を通す。

### 3.6 費用と失敗

- 費用の上限は二重にする：① 1 回の中で使った量を数え、上限に届いたら止める ② Anthropic のコンソールで月の上限を決める。値は人が決める【要確認：値】。
- 失敗（API の失敗・費用の上限・検証器のエラー）は、それ以上進めずに止めて記録する。勝手に作り直して進めない。
- 書き込みの見張りに止められたら、回り道をせずに止まって記録する。
- ループの Claude に渡す道具は、作業フォルダの読み書き・採点の実行・PR を出すことに絞る。ウェブには出さない。
- ループのログに、公開 PDF から取り出した氏名などの中身は書かない。件数・時刻・エラーの種類と、団体をたどれない形の判断の説明だけにする。

### 3.7 記録

回るたびに、`docs/evolution.md` に次を残す（今と同じ書式）。

- ルールの改善の 1 行（PR の本文に書き、マージのあとに足す）。
- ループの量：挙げた候補の数、反証で落とした数、出した PR の数、取り込み・却下と理由、かかった時間と費用。
- Claude の判断と人の判断の一致：人が確かめた N 件中 X 件で一致。

### 3.8 できたかの基準

1. 人が 1 回起こすと、束を読み、候補を挙げ、反証し、歯止めを通ったものの PR を出して止まる。
2. その PR を人がマージすると、今の配信の手順で検査器に入る。却下すると、理由が記録に残る。
3. 新しい版の検査器が、前の版では見つからなかった合成 PDF の漏れを見つける。ほかの型の点は下がらない。
4. その間ずっと、検査器の外への要求は 0 件のまま（`npm run check:browser`）。

## 4. この先（期間中は作らない・動かさない）

### 4.1 定時の自動の実行

- 1 回分の道具（§3）を、決まった時刻に起動する（CLAUDE.md §4-1 の 5:00・20:00 など）【要確認：予定タスクか、別の起動の仕方か】。
- 予定タスクの中で、書き込みの見張りが同じように効くかを先に確かめる（`docs/write-guard.md` の「まだ確かめていないこと」）。
- 定時に回しても、マージは人がする。配られるのは承認したときだけなので、画面や README に「毎晩更新」とは書かない。
- 朝に、前の回の要約（読んだ数、候補の数、届かなかった数、費用、止まった理由）を 1 か所で見られるようにする【要確認：置き場所】。

### 4.2 集める BOT

**期間中は、ウェブに向けて動かさない。** 作るとしても、試運転（どこを取りに行くかの計画を出すだけで、実際には取りに行かない）まで。本番で動かすかは、期間のあとに人が決める。

動かすときの決まり（コードと README に公開する）：

- 公開されている PDF だけ。robots.txt に従う。
- 同じホストへの間隔を空ける【要確認：値】。1 日に回る数に上限を設ける【要確認：値】。同じ所に続けて行かない。選んだ理由の種類を記録する（団体名は書かない）。
- 拒否・制限（429・503・401/403 の連続）を受けたホストには、自動では二度と行かない。
- User-Agent に作品の URL を入れる。
- 原文は非公開の置き場にだけ置く。外に出すのは統計だけ。
- 語り方は「学ぶ材料を集める」。「見張る」「監視」とは言わない。

### 4.3 外す

- 誤検知が多いルール、古くなったルールを、外す候補として PR で出す。外すのも §3.4 の歯止めで測り、承認を通す。
- 外してよいのは、**外す理由が誤検知を減らすことで、漏れの検出は下がらない**ときだけ。誤検知が減ることが「良くなる 1 つ」になるので、§3.4 の歯止めとそのまま両立する。外すと、どれか 1 つの型でも検出が下がるなら、外さない。

### 4.4 ルールをデータとして持つ

今のルールはコードなので、ルールを足すたびに検査器のコードが変わる。この先、決まった検出の種類（`kind`）と片付けの種類（`fix`）をコードに持ち、ループが足すのはそれを組み合わせたルールのファイル（JSON など）だけにする案がある。新しい `kind`・`fix` が要るときだけ、コードの変更の PR にする。

案の形（決まっていない）：

```json
{
  "id": "author-personal-name-001",
  "status": "active",
  "kind": "metadata_match",
  "params": { "field": "Author" },
  "fix": "rewrite_metadata",
  "severity": "high",
  "why": "作成者欄に個人の名前が残っています。公開すると、誰が作ったかが分かります。",
  "added_in": "2026.11.05-1"
}
```

- `status` は `active` か `retired`。決めきれないものは `severity: "review"` で「確かめてください」と理由を出す。
- 片付けで消せないものは `fix: "manual"` とし、手で直す方法を添える。
- 今の `rules/` のコードと、どう移り変わるか【要確認】。

### 4.5 画面に「育っている」ことを出す

- 今の「ルールの版」（§2）を、ルールを足すたびに手で直さずに済むようにする（記録から作る）【要確認】。
- 指摘 1 件ごとの由来（足した日・PR 番号・点数）は、たたんだ「詳しく」の中だけに置く。利用者が知りたい「安全か、どこが危ないか、どう直すか、直ったか」を邪魔しない。
- 「前は危なかった」と思わせる書き方はしない（新しい型を足した、と言う）。

### 4.6 ほかの分野へ

流れ（読む → 候補 → 測る → PR → 人が承認 → 配る → 外す）は共通にし、分野ごとに差し替えるのは 4 つだけにしておく：集める先、ルールの書式、検証器（正解データ）、見つけたときの対処。たとえば、毎日公開される脆弱性情報を読み、自分のシステムが当てはまるかのルールにする、といった使い方を想定している（作らない。想定まで）。

## 5. 決めること（【要確認】の一覧）

- 定時の自動の実行を、今どこまで始めているか（§2 の最後）。
- 1 回に読む数（まず 50 件）、モデルの選び方、費用の上限の値。
- 候補の JSON スキーマ。
- Claude が直す回数の上限。
- 却下の理由を、次の回のループにどう読ませるか。

決まったこと（2026-11-06、人の決定）：

- 歯止めは「どれも下がらず、少なくとも 1 つは良くなる」。すべてが同じままの候補は入れない（§3.4）。
- 外すのは、外す理由が誤検知を減らすことで、漏れの検出は下がらないときだけ（§4.3）。
- ルールをデータとして持つか、持つならいつ・どう移すか。
- 集める BOT の間隔・1 日の上限（作る場合）。
