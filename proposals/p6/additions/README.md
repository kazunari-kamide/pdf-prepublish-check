# 合成 PDF を足す案：P6（見せかけの黒塗り）

PR #6 の決めてほしいこと 3 への返事（「半透明の黒・円や斜めの四角・重いページの合成 PDF を足す案は、proposals/p6/ に出してよい。移すのは人」）に沿った案。

検出ルールの判定の値のうち、合成 PDF に試す例がなく、測れていないものがある（`rules/p6-text/README.md`）。その値を測れるように、次の例を足す。

| 値 | いまの値 | 足す例 |
|---|---|---|
| 塗りを「隠している」とみなす不透明さの下限 | 0.9 | 不透明さ 0.95（漏れ）、0.3・0.6（漏れでない） |
| 塗りを「四角に近い」とみなす割合 | 0.9 | 楕円、1度・3度回した四角、角の丸い四角（漏れ）。字のない所の円・斜めの帯（漏れでない） |
| 1ページの命令の数の上限 | 20 万【仮の値】 | 曲線 12 万本のページ（命令は 36 万） |

## 中身

```
proposals/p6/additions/
  build-additions.mjs                  追加の合成 PDF と正解データを作るスクリプト
  fixtures/p6/*.pdf, *.expected.json   作った結果（8 個。漏れ 7 件、漏れでないもの 5 件）
  fixtures/p6/index-additions.md       一覧
  fixtures/p6/hashes-additions.txt     SHA-256
```

- `fixtures/p6/build.mjs` を書き換えず、別のスクリプトにした。理由：このスクリプトを書いたセッションは、検出ルールを書いたセッションで、検証器の中身と `build.mjs` を読んでいない（独立を保つため）。`build.mjs` を読まずに書き換えることはできないので、別にした。
  - そのため、字は `build.mjs` の BIZ UDゴシックではなく、標準の Helvetica（ASCII の架空の名前だけ）にした。正解データの形は `fixtures/p6/README.md` に合わせた。
- 一覧と SHA-256 は、既存の `index.md`・`hashes.txt` を上書きしないように、別の名前にした。

## 移し方（人が行う）

```
git mv proposals/p6/additions/build-additions.mjs fixtures/p6/build-additions.mjs
git mv proposals/p6/additions/fixtures/p6/* fixtures/p6/
git commit -m "P6 の合成 PDF を足す（半透明・四角でない覆い・重いページ）"
```

- `build-additions.mjs` は、置かれた場所が `fixtures/p6/` なら同じフォルダに書く。移したあとも書き換えは要らない。
- **移すと、`node verifier/selfcheck.mjs` は不合格になる**（下の表の「検証器」で見逃しているもの）。これは検証器の限界（`verifier/README.md`：四角でない覆いは数えない）が、正解データとして表に出たもの。移す前に、決めてほしいこと 2 を決める必要がある。

## 確かめた結果（2026-11-03、Node 24.19.0、Windows）

検証器（`node verifier/cli.mjs`）と、検出ルール `p6-text` 1.1.0 にかけ、`eval/match.ts` と同じ照らし合わせ方（重なり 50% 以上、同じページ・同じ層、1対1）で正解と比べた。字数は、PDF.js で取り出した字の数（空白を除く）。

| ファイル | 取り出せた字数 | 検証器 | 検出ルール 1.1.0 |
|---|---|---|---|
| p6-t13-opaque-095（不透明さ 0.95） | 10 | 1 件中 1 件 | 1 件中 1 件 |
| p6-d07-translucent-03（0.3） | 10 | 反応なし | 反応なし |
| p6-d08-translucent-06（0.6） | 12 | 反応なし | 反応なし |
| p6-t14-ellipse（楕円） | 10 | **1 件中 0 件** | **1 件中 0 件** |
| p6-t15-rotated-rects（1度・3度） | 23 | **2 件中 1 件**（3度を見逃し） | **2 件中 1 件**（3度を見逃し） |
| p6-t16-rounded-rects（角の半径 3・高さの半分） | 19 | **2 件中 1 件**（半径が高さの半分のものを見逃し） | **2 件中 0 件** |
| p6-d09-shapes-no-text（字のない円・斜めの帯・黒い丸の上の白い字） | 3 | 反応なし | 反応なし |
| p6-h01-heavy-page（1ページ目に曲線 12 万本） | 0 / 10 | 1 件中 1 件。**1ページ目を省かずに読んだ**（全体で 652 ms） | 1 件中 1 件。1ページ目を省いた（112 ms） |

- どちらも、正解にない報告・漏れでないものへの報告は 0 件。
- `build-additions.mjs` を3回続けて実行し、PDF・正解データ・一覧の SHA-256 がすべて同じだった。既存の `fixtures/p6/` は変わらず、`node verifier/selfcheck.mjs` は「すべて正解データと合った」のまま。
- 字が描けているかは、PDF.js で字を取り出して数えた（上の表）。**画像にして目で見る確かめは、していない**（Node で描く道具がないため）。移す前に、ビューアーで開いて見てほしい。

### 表から分かったこと

- **角の丸い四角（半径 3）で、検証器と検出ルールの答えが分かれた。** 検出ルールは、曲線を含む図形をすべて覆いとして扱わない（`rules/p6-text/page.ts` の `paint`）。検証器は、曲線の端の点を結んだ形で四角らしさを測っているようだ（推測。検証器の中身は読んでいない）。検出ルールの側で直せる見逃し。移したあとに、検出ルールを直す PR を別に出す。
- **重いページでは、検証器は省かず、検出ルールは省いた。** 検出ルールは命令の数（36 万 ＞ 上限 20 万）で省く。検証器の上限は 30 万だが、PDF.js が曲線の命令を1つにまとめて数えるため、上限に届かなかったようだ（推測）。
  - 1ページの重さは、内容 約 6.4 MB（圧縮を解いた大きさ。測った値）。CLAUDE.md §5 の例（曲線 約 8 万個、内容 3.6 MB）より重いが、検証器は 652 ms で読み終えた。§5 の例で止まったのは、字の取り出しと図形の取り出しの方で、ここで使った読み方ではない可能性がある（推測）。

## 決めてほしいこと

1. **どの不透明さから「漏れ」とするか。** 案では、0.95 を漏れ、0.3・0.6 を漏れでないもの（`translucent_mark`）にした。0.85 前後は判断が分かれるので、入れていない。
   - 案：字と背景の見え方で決める。黒い字の上に不透明さ a の黒を重ねると、背景の明るさは 1−a になる。0.9 なら 0.1 で、黒い字とほぼ区別できない。
2. **四角でない覆いの型（楕円・3度回した四角・丸い角の四角）を、正解データに入れるか。**
   - 入れる（案）：本物の漏れなので、正解データにある方がよい。ただし、検証器が見逃すので、検証器そのものの確かめが不合格になる。検証器を直す（人か、検出ルールを読まない別のセッション）か、正解データに「検証器が見逃す型」のしるしを付けるか、を決める必要がある。
   - 入れない：検出ルールのテストの中でだけ確かめる。
3. **重いページの正解データの形。** 案として `expected_skipped_pages: [1]`（このページは省いてよい／省くはず）を足した。ただし、上のとおり、検証器は省かなかった。
   - `rubric/p6.json` は「`skipped_pages` があれば、片付けたあとの残り 0 件と数えない」としている。片付けの採点は検証器で行うので、検証器が省かなければ影響はない。検出ルールが省いたページの漏れを、検出率の分母に入れるかを決めてほしい（いまの eval では、省いたページの漏れは見逃しとして数える）。
   - 重いページの PDF は約 2.3 MB ある。リポジトリに入れてよいか。
4. **新しい kind（`translucent_mark`・`decorative_shape`）を、`fixtures/p6/README.md` の表に足すか。**
